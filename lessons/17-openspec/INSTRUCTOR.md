# Преподавание спецификации через OpenSpec

Перед занятием прочитайте [руководство преподавателя](../../course/TEACHER_GUIDE.md): оно задаёт порядок подсказок, возврата к исходной ошибке и проверки самостоятельного переноса.

## Вход в занятие до прогнозов

Прочитайте с учеником [введение](INTRO.md). Сначала прочитайте только первый абзац задания и найдите два исходных документа. Попросите ученика объяснить их роль и действие при противоречии, затем проверьте реальные результаты урока 16. Последовательность CLI и прогноз артефактов вводите после ориентации; фраза в шаблоне не доказывает состоявшееся согласование.

Если ученик не понимает, зачем вводить команду или какой текст читать, вернитесь к её назначению, точному объекту и ожидаемому виду результата. Продолжайте после его объяснения своими словами, а не после одного «готово».

## Подготовка преподавателя

До урока проверь контейнерный образ llm-course-sandbox:1.0 без установки пакетов во время действий агента. В нём нужны Bash, Node, OpenSpec 1.16.0 и доступные локально схемы OpenSpec. Версию на хосте и версию в контейнере фиксируй отдельно.

Прочитай реальные решения из занятия 16. HEADLESS.md — предложенный технический контракт приёмки, а не скрытая подмена пользовательских решений. Если ученик выбирает иные правила, обновите профиль независимой проверки до реализации.

Не проводи урок по заранее придуманной трассе. Синтетическая незавершённая спецификация в fixtures предназначена только для упражнения по сопоставлению требований.

## План на 80 минут

| Минуты | Работа преподавателя |
| --- | --- |
| 0–10 | Проверить решения, границы задачи и контракт приёмки |
| 10–25 | Наблюдать реальный CLI, объяснить роль инструкций |
| 25–45 | Сопоставить пять решений со сценариями и задачами |
| 45–60 | Ученик меняет одно решение, проверяет согласованность |
| 60–70 | Разобрать validate и отсутствие кода игры |
| 70–80 | Получить явное согласование, подготовить передачу в занятие 18 |

Для 60 минут используй заранее подготовленную среду и ограничь изменение одним значением. Для 90 минут добавь отрицательное упражнение: спецификация с правильными заголовками, но без сценария для выхода. Не сокращай настоящую проверку до чтения названий файлов.

## Вопросы и ответы преподавателю

1. Кто пишет текст спецификации? Модель; CLI выдаёт структуру, инструкции и проверки.
2. Почему new change не означает «план готов»? Команда только создаёт изменение; содержательные артефакты ещё предстоит заполнить.
3. Чем status отличается от проверки игры? Status показывает готовность артефактов по схеме, а не результат игрового цикла.
4. Что доказывает validate? Соответствие поддерживаемым структурным требованиям; правильность требований пользователя всё равно проверяется отдельно.
5. Может ли пользователь изменить решение после появления proposal? Да. Нужно обновить зависимые требования и задачи, сохранив смысл изменений.
6. Где хранить независимую приёмку? В защищённых материалах курса вне каталога, который агент может переписать.
7. Почему не использовать существующий Codex для создания документов? В этом курсе исследуется наш собственный harness. Скрытая замена агента нарушает эксперимент.

## Типичные заблуждения

«OpenSpec — дополнительная модель». Покажи вызов CLI и обычные файлы, затем отдельный вызов ядра модели.

«Валидация зелёная, значит игра правильная». Попроси указать выполненный сценарий игрового поведения; в этом занятии такого свидетельства ещё нет.

«Все задачи отмечены, значит работа завершена». Чекбокс — утверждение; ему нужны результаты проверки и ручная приёмка.

«Можно сразу принять рекомендованные решения навыка». Рекомендация облегчает выбор, но становится требованием только после ответа пользователя.

## Вмешательства преподавателя

Если CLI недоступен в контейнере, возвращаемся к подготовке стенда, а не разрешаем установку из сети. Если агент не видит stderr, разбираем трассу передачи наблюдения. Если он переписывает требования, чтобы упростить реализацию, ученик должен найти расхождение с защищённой копией согласования.

Если модель исчерпала бюджет, фиксируем частичный результат. Для отдельного продолжения формулируем ограниченную задачу: какой артефакт и по какому наблюдению нужно исправить. Не сбрасываем историю неудач ради красивой итоговой статистики.

## Разбор синтетического примера

В fixtures/incomplete-mapping.json намеренно отсутствует проверка восстановления терминала. Ученик должен обнаружить пробел до просмотра ответа. Формат документов и их имена сами по себе не покрывают это поведение.

## Дополнительный опыт

Сравнить агенту две версии требования: «выход по q» и «после q процесс завершается, курсор и настройки терминала восстановлены». Обсудить, какие части можно проверить автоматически, а какие остаются ручными. Не требовать буквального совпадения формулировок.


## Совместное наблюдение в терминале

Используйте [общий порядок совместного занятия](../../course/TERMINAL_CLASSROOM.md). Ученик открывает `./lab classroom start --lesson 17 --sandbox-image llm-course-sandbox:1.0`. Преподаватель находит сессию через `./lab classroom list`, читает события через `observe SESSION --json` и просит прогноз до первого запуска.

Для этого этапа исходный набор компонентов: `./lab classroom permit SESSION --capabilities doctor,complete,agent,bash,skill`. После проверки подготовки преподаватель выполняет `./lab classroom resume SESSION`. На разборе результата он использует `pause`, для прерывания активного опыта — `stop` и проверяет фактическое подтверждение.

Советы передавайте через `./lab classroom advise SESSION --message 'Текст следующего вопроса или опыта'`. Ученик отвечает и меняет вход самостоятельно. Дополнительные программы из методички, не подключённые к диспетчеру, обсуждайте отдельно: открытая консоль сама по себе не даёт наблюдение и остановку всех процессов ноутбука.
