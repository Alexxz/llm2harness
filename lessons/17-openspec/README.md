# Спецификация игры через OpenSpec

Сначала прочитай [введение и первый шаг](INTRO.md): там объяснены смысл опыта, участники и конкретный текст для чтения. Блоки подготовки и опытов ниже предназначены для обычного Bash-терминала. В приглашении `ученик>` используй команды учебной консоли из введения и указаний преподавателя.

В этом занятии наш агент превратит согласованные решения в проверяемые требования и задачи. Он вызовет настоящий OpenSpec CLI внутри подготовленного контейнера. Результатом будут артефакты изменения и твой ответ о готовности переходить к реализации.

Для совместной работы открой [учебную консоль с преподавателем](../../course/TERMINAL_CLASSROOM.md): `./lab classroom start --lesson 17 --sandbox-image llm-course-sandbox:1.0` из корня проекта. Промпты, явные запуски и советы этой сессии видны преподавателю; обычные команды других терминалов в журнал не попадают.


## Цель

Различать три события: человек согласовал требования, OpenSpec проверил структуру спецификации, игра прошла проверку поведения. Первые два события доступны в этом занятии; третье относится к занятию 18.

## Перед началом

Нужны результаты интервью из занятия 16 и заранее подготовленный образ llm-course-sandbox:1.0 с Bash, Node и OpenSpec 1.16.0. Сборка образа, получение зависимостей и проверка Docker выполняются до занятия по общему ресурсному плану. Сеть во время действий агента отключена. Отсутствующий образ не должен вызывать автоматическую загрузку или запуск OpenSpec на хосте.

    mkdir -p results/17 work/snake
    /usr/bin/python3 -m coursekit doctor
    openspec --version

Последняя команда показывает версию доверенного CLI на машине ученика. Для приёмки агент должен отдельно получить версию CLI внутри своего контейнера через run_bash. Наличие программы на хосте не означает её наличие в среде агента.

Создай results/16/agreed-requirements.md по итогам настоящего интервью. Шаблон requirements-template.md помогает проверить полноту, но не заменяет принятые тобой решения.

    cp results/16/agreed-requirements.md work/snake/requirements.md
    cp lessons/18-snake/HEADLESS.md work/snake/acceptance-contract.md

Прочитай технический контракт headless-проверки. Это предлагаемое условие проверяемости игры; согласуй его с агентом вместе с игровыми правилами. Если меняешь базовые правила столкновений, сначала согласуй соответствующие изменения проверок.

Защищённая копия согласованных требований и контракт проверки остаются вне work/snake. Агент сможет изменять рабочие документы, но не должен менять исходные критерии ради прохождения теста.

## План занятия

| Минуты | Действие |
| --- | --- |
| 0–10 | Проверить согласованные решения и технический контракт |
| 10–25 | Наблюдать создание изменения и получение инструкций |
| 25–50 | Читать требования, сценарии, дизайн и задачи |
| 50–65 | Внести одно изменение в решение и обновить артефакты |
| 65–80 | Проверить соответствие, статус CLI и границу реализации |

## Опыты

### Агент создаёт изменение

    /usr/bin/python3 -m coursekit agent \
      --task-file lessons/17-openspec/prompts/baseline.txt \
      --workspace work/snake \
      --endpoint http://127.0.0.1:8088 \
      --skill skills/grill-me.md \
      --tools read_file,write_file,run_bash,ask_user,finish \
      --sandbox-image llm-course-sandbox:1.0 \
      --max-steps 32 \
      --max-requests 48 \
      --max-tokens 4096 \
      --timeout 300 \
      --deadline-seconds 1200 \
      --state results/17/planning-state.json \
      > results/17/planning.json

В трассе ищи фактические вызовы CLI и их коды завершения. Для OpenSpec 1.16.0 ожидаются команды этого вида:

    openspec --version
    openspec --no-color init --tools none --language Russian --no-animation
    openspec new change snake-bash --schema spec-driven --json
    openspec status --change snake-bash --json
    openspec instructions proposal --change snake-bash --json
    openspec instructions specs --change snake-bash --json
    openspec instructions design --change snake-bash --json
    openspec instructions tasks --change snake-bash --json
    openspec validate snake-bash --strict --json --no-interactive

Агент выполняет их по зависимостям, а не одной слепой пачкой. При уже существующем проекте и изменении он сначала читает состояние. Не создавай повторное изменение ради устранения ошибки команды.

OpenSpec создаёт структуру и сообщает инструкции. Содержимое proposal.md, specs, design.md и tasks.md пишет модель через инструменты harness. CLI не превращает неуточнённый замысел в требования самостоятельно.

### Читаем спецификацию как пользователь

Открой документы в work/snake/openspec/changes/snake-bash. Для каждого твоего решения найди явное требование и проверяемый сценарий. Особенно проверь управление, рост и счёт, столкновения, выход, восстановление терминала и headless-контракт.

В tasks.md должны быть отдельные задачи для реализации, независимой автоматической проверки и ручной игры. Галочки реализации пока не проставляются.

Выпиши один пример:

- Решение пользователя: выход по q.
- Требование: нажатие q завершает игровой цикл и возвращает управление терминалу.
- Проверка: ручной выход плюс сравнение настроек терминала до и после.

Сам факт наличия слов «выход по q» в документе не доказывает работоспособность.

### Меняем одно решение

Прочитай prompts/variation.txt и создай results/17/revision.txt с одним действительным изменением твоего решения. Например, измени размер поля по умолчанию. Не отправляй пример бездумно, если он противоречит твоему замыслу.

    /usr/bin/python3 -m coursekit agent \
      --workspace work/snake \
      --endpoint http://127.0.0.1:8088 \
      --skill skills/grill-me.md \
      --tools read_file,write_file,run_bash,ask_user,finish \
      --sandbox-image llm-course-sandbox:1.0 \
      --max-steps 32 \
      --max-requests 48 \
      --max-tokens 4096 \
      --timeout 300 \
      --deadline-seconds 1200 \
      --resume results/17/planning-state.json \
      --answer-file results/17/revision.txt \
      > results/17/revision.json

Проверь, что изменение согласованно отражено в требованиях, сценариях и задачах. Если агент задаёт следующий раунд, ответь на него отдельным файлом. Запрос на изменение не означает согласие со всем остальным.

### Согласование перед реализацией

После прочтения актуальных артефактов отправь явный ответ, например: «Спецификация и критерии проверки согласованы. Обсуждение требований завершено. Реализацию начнём отдельным запуском занятия 18».

Агент завершает именно задачу подготовки спецификации. В этом занятии игрового файла snake.sh ещё быть не должно. Запрет писать игру сейчас является проверяемым требованием задания; текущие технические политики ограничивают инструменты и каталог, а не распознают назначение каждого создаваемого файла.

## Ожидаемые наблюдения

Вызовы version, new, instructions, status и validate оставляют настоящие наблюдения инструмента. Появляются артефакты OpenSpec, а их содержимое зависит от твоих ответов.

Успешная структурная валидация означает соответствие правилам OpenSpec. Корректность продуктовых решений проверяешь ты. Пустая или слишком общая спецификация может быть бесполезной даже при подходящей структуре.

Строка /opsx:apply в нашем простом CLI не является встроенной командой. В учебном harness модель должна вызвать реальный инструмент и прочитать инструкции; название slash-команды само по себе ничего не выполняет.

## Если результат отличается

Если OpenSpec отсутствует внутри контейнера, остановись на подготовке образа. Не устанавливай пакет во время вызова модели и не включай сеть как обход.

Если CLI требует другой формат артефакта, сохрани stderr и инструкцию именно установленной версии. Ошибка не исправляется выдуманным «успешным» ответом инструмента.

Если агент начал писать игру до согласования, опыт считается нарушенным. Останови его, сохрани трассу и отдели незапрошенные изменения перед новым запуском. Не используй их как доказательство качества этапа спецификации.

Если бюджет закончился до приёмки, сохрани результаты и сузь отдельный следующий запуск до оставшегося артефакта. Не объявляй план готовым по частично заполненным файлам.

## Что сохранить

Сохрани исходные решения, изменение решения, защищённое состояние и трассу, артефакты OpenSpec, результат validate и собственный ответ о согласовании. Добавь таблицу «решение → требование → проверка» хотя бы для пяти правил.

## Критерии завершения

- Агент вызвал настоящий OpenSpec внутри подготовленного контейнера и получил результаты.
- Каждое существенное решение из интервью отражено в спецификации или явно исключено.
- Есть независимые критерии поведения игры, а не только проверка синтаксиса.
- Одно изменение пользователя согласованно обновило связанные артефакты.
- Человек подтвердил актуальную спецификацию; игра ещё не реализована.

## Свой эксперимент

Замени одно чёткое требование на расплывчатое, например «управление должно быть удобным». Попроси агента проанализировать проверяемость без реализации. Сравни этот анализ с настоящими сценариями клавиатурного управления и восстанови согласованную версию требования.
