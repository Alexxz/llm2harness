# Проведение занятия о MCP

Перед занятием прочитайте [руководство преподавателя](../../course/TEACHER_GUIDE.md): оно задаёт порядок подсказок, возврата к исходной ошибке и проверки самостоятельного переноса.

## Вход в занятие до прогнозов

Прочитайте с учеником [введение](INTRO.md). Начните с информации, которую требуется получить из заметки, и указанного маршрута чтения. Проверьте, что ученик различает показ задачи через `show`, настоящий вызов инструмента и отдельный запрос к модели. Имена протокольных сообщений и прогноз обмена вводите после простой схемы двух программ.

Если ученик не понимает, зачем вводить команду или какой текст читать, вернитесь к её назначению, точному объекту и ожидаемому виду результата. Продолжайте после его объяснения своими словами, а не после одного «готово».

## Подготовка

Проверьте `mcp_experiment.py --self-test` на настоящем локальном клиенте и сервере. Для задания модели отдельно подготовьте ядро; успех stdio-проверки не доказывает, что модель умеет выбирать инструмент. В используемом сервере только `read_note`, разрешён только назначенный каталог и ограничен размер содержимого.

Покажите ученику, что subprocess запускается фиксированной программой курса, без shell. Сетевой endpoint модели и канал stdio MCP — разные соединения. Для протокольного опыта не требуется доступ к внешним системам, установка SDK или Docker. В обеих live-командах явно задано `--tools read_file,write_file,mcp_call`: флаг подключения и разрешение действия видны отдельно. Не полагайтесь на скрытый набор инструментов по умолчанию. До первого запроса модели runtime должен получить реальные дескрипторы через `tools/list` и включить их в контекст.

## Ход занятия

| Минуты | Действие ученика | На что обратить внимание |
| --- | --- | --- |
| 0–10 | Рисует участников и прогнозирует сообщения | Не соединяет ли модель с файловой системой напрямую |
| 10–25 | Запускает mcp-demo и находит сообщения по id | Различает ли request, notification и response |
| 25–40 | Проверяет схему, неверные параметры и выход за каталог | Различает ли ошибку протокола и ошибку инструмента |
| 40–60 | Сравнивает direct и MCP на одной заметке | Есть ли именно tools/call после решения модели |
| 60–70 | Подменяет только синтетическую заметку версией B | Откуда появился новый факт в ответе |
| 70–75 | Объясняет границы доверия и завершение процесса | Понимает ли пределы демонстрации |

До 90 минут добавьте опыт с отключённым MCP и обсуждение таймаута клиента. Не направляйте агента к реальным внешним серверам для демонстрации отказа.

## Вопросы с ответами

**Почему `tools/list` не является вызовом полезной операции?** Это обнаружение метаданных и схем. Для чтения заметки нужен отдельный `tools/call`; его результат содержит фактические данные.

**Кто вызывает MCP: нейросеть или программа?** Модель формирует предложение действия. Программа проверяет его и выполняет запрос через клиент. Название «model-controlled tools» не отменяет этого разделения исполнения.

**Появляется ли у модели новый факт после подключения одной схемы?** Схема описывает допустимый вызов. Данные заметки поступают после выполнения и добавления результата в контекст.

**Зачем stdout и stderr разделены?** stdout — транспорт протокольных сообщений. Произвольные диагностические строки нарушают разбор; stderr остаётся каналом диагностики.

**Почему `isError: true` может прийти в нормальном JSON-RPC result?** Сам запрос корректен, но операция инструмента не смогла выполнить задачу. Это отличается от ошибки формы RPC-вызова.

**Доказывает ли правильный ответ `q` и `p`, что модель использовала MCP?** Нет. Нужны предложенное действие, фактический вызов клиента и его результат; модель могла использовать прямой инструмент или угадать ответ.

**Стал ли отдельный процесс полноценной песочницей?** Нет. Здесь доверенный сервер ограничивает свой узкий интерфейс и проверяет путь. Произвольный сгенерированный код требует отдельной OS-изоляции.

## Типичные заблуждения и вмешательства

При фразе «MCP научил модель читать» предложите заменить только содержимое заметки и показать данные в следующем запросе. При поиске подтверждения по одному answer потребуйте соответствующий `tools/call`. Если ученик считает слово readOnly гарантией доступа, укажите, где сервер на самом деле проверяет путь и какие аргументы отклоняет.

Если baseline использует MCP вместо direct или variation использует direct, сохраните это как ошибку выбора маршрута. Не меняйте оценку ради красивого одинакового финального ответа. Добавление точной инструкции о маршруте — допустимый новый опыт, который нужно назвать новым, а не незаметно заменить исходный.

## Сокращение до 60 минут

Оставьте протокольную трассу, отрицательные проверки и один live-вызов через MCP. Прямой маршрут и замену версии заметки можно завершить самостоятельно. Требование показать фактическое взаимодействие с отдельным сервером остаётся обязательным.

## Приёмка

Разделяйте три результата: протокольный обмен состоялся; сервер соблюдает заданные границы; настоящая модель выбрала нужный маршрут и использовала данные. Каждый результат нуждается в своём свидетельстве. Успешный тест на фикстуре закрывает первые механические проверки, но не live-часть занятия.

## Совместное наблюдение в терминале

Используйте [общий порядок совместного занятия](../../course/TERMINAL_CLASSROOM.md). Ученик открывает `./lab classroom start --lesson 15`. Преподаватель находит сессию через `./lab classroom list`, читает события через `observe SESSION --json` и просит прогноз до первого запуска.

Для этого этапа исходный набор компонентов: `./lab classroom permit SESSION --capabilities doctor,complete,agent,mcp`. После проверки подготовки преподаватель выполняет `./lab classroom resume SESSION`. На разборе результата он использует `pause`, для прерывания активного опыта — `stop` и проверяет фактическое подтверждение.

Советы передавайте через `./lab classroom advise SESSION --message 'Текст следующего вопроса или опыта'`. Ученик отвечает и меняет вход самостоятельно. Дополнительные программы из методички, не подключённые к диспетчеру, обсуждайте отдельно: открытая консоль сама по себе не даёт наблюдение и остановку всех процессов ноутбука.
