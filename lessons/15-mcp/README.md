# Подключение инструмента через MCP

Сначала прочитай [введение и первый шаг](INTRO.md): там объяснены смысл опыта, участники и конкретный текст для чтения. Блоки подготовки и опытов ниже предназначены для обычного Bash-терминала. В приглашении `ученик>` используй команды учебной консоли из введения и указаний преподавателя.

Для совместной работы открой [учебную консоль с преподавателем](../../course/TERMINAL_CLASSROOM.md): `./lab classroom start --lesson 15` из корня проекта. Промпты, явные запуски и советы этой сессии видны преподавателю; обычные команды других терминалов в журнал не попадают.


## Цель

Подключить настоящий отдельный процесс с MCP-инструментом и проследить полный путь запроса. Модель выбирает действие, harness вызывает MCP-клиент, сервер выполняет разрешённую операцию и возвращает результат. Веса модели не меняются.

В практике зафиксирован небольшой учебный профиль протокола `2025-06-18`. Сначала клиент и сервер согласуют возможности через `initialize`, затем клиент отправляет `notifications/initialized`. Доступные инструменты получают через `tools/list`, а вызывают через `tools/call`. Это обмен между программами; для него не нужна языковая модель. См. [жизненный цикл MCP](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle).

## Перед началом

Нужны `/usr/bin/python3`, jq и материалы занятий 08, 12 и 14. Для первых двух опытов модель, сеть и Docker не требуются. Для последнего нужен ранее подготовленный сервер ядра. Все файлы заметок синтетические.

```bash
mkdir -p results/15/control results/15/workspace
cp lessons/15-mcp/fixtures/notes-a.txt results/15/workspace/notes.txt
/usr/bin/python3 -m coursekit doctor
```

Клиент запускает фиксированный сервер курса с одним инструментом чтения заметки. Он не подключается к внешним MCP-серверам и не позволяет модели выбирать произвольную программу для запуска. Отдельный процесс сам по себе не является OS-песочницей: здесь это доверенная программа с узким интерфейсом и проверками путей. Сгенерированный код по-прежнему исполняется только в изоляции занятия 12.

## План занятия

75 минут: 10 на схему взаимодействия, 20 на живой локальный протокол без модели, 15 на отклонение неправильных запросов, 20 на два маршрута вызова моделью и 10 на объяснение трассы. Подготовку весов выполнить заранее.

## Опыты

### Проследи протокол без модели

Открой `fixtures/protocol-example.json`. Это заранее составленная последовательность для чтения, а не журнал реального запуска. Предскажи, на какие сообщения сервер отвечает и где связываются `id` запроса и ответа.

Теперь запусти настоящий клиент и отдельный сервер:

```bash
/usr/bin/python3 -m coursekit mcp-demo --workspace results/15/workspace > results/15/control/mcp-demo.json
jq '.tools' results/15/control/mcp-demo.json
jq '.events[] | select(.event == "mcp_send" or .event == "mcp_receive") | {event, message}' results/15/control/mcp-demo.json
```

В отправленных сообщениях ожидается порядок `initialize` → `notifications/initialized` → `tools/list` → `tools/call`. У уведомления `notifications/initialized` нет `id` и отдельного ответа. Наличие подключённого клиента или списка инструментов ещё не доказывает, что инструмент был вызван; найди именно `tools/call` и соответствующий результат.

При stdio отдельные JSON-RPC сообщения разделяются переводами строки, а диагностические сообщения сервера должны идти в stderr, не смешиваясь с протоколом stdout. Это требование [stdio-транспорта MCP](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports). В JSON поле `text` может содержать экранированный перевод строки внутри строки; это не разделитель сообщения.

### Проверь входы и границы инструмента

Запусти небольшой проверяемый опыт. Он создаёт временные синтетические файлы, запускает настоящий сервер, делает запросы и закрывает дочерний процесс. Модель не вызывается.

```bash
/usr/bin/python3 lessons/15-mcp/mcp_experiment.py --self-test > results/15/control/mcp-checks.json
jq '{kind, checks}' results/15/control/mcp-checks.json
```

Ожидаются успешные проверки обнаружения схемы, чтения заметки, отказа лишнему полю аргументов, неизвестному имени инструмента и выходу за назначенный каталог. После ошибочных аргументов валидный запрос должен по-прежнему работать. По закрытии клиента процесс сервера завершается.

Различай два исхода. Неправильные параметры протокольного вызова возвращают JSON-RPC ошибку; невозможность прочитать указанную заметку возвращает результат инструмента с `isError: true`. Успех доставки сообщения не доказывает успех операции. Структура инструментов и результатов описана в [MCP Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools).

Менять `description` инструмента недостаточно для запрета опасного пути: проверку исполняет сервер. Клиент также не должен доверять тексту результата как системной инструкции.

### Сравни прямой инструмент и MCP на одной модели

В двух запусках включён один и тот же набор возможностей, одна модель, одинаковые данные и лимит шести шагов. В промпте меняется только требуемый маршрут чтения: `read_file` или MCP. Названия MCP-инструментов агент получает из обнаруженных схем.

```bash
/usr/bin/python3 -m coursekit agent --task-file lessons/15-mcp/prompts/baseline.txt --workspace results/15/workspace --endpoint http://127.0.0.1:8088 --max-steps 6 --mcp --tools read_file,write_file,mcp_call --state results/15/control/direct-state.json > results/15/control/direct.json
/usr/bin/python3 -m coursekit agent --task-file lessons/15-mcp/prompts/variation.txt --workspace results/15/workspace --endpoint http://127.0.0.1:8088 --max-steps 6 --mcp --tools read_file,write_file,mcp_call --state results/15/control/mcp-state.json > results/15/control/mcp-agent.json
jq '{status, answer}' results/15/control/direct.json
jq '{status, answer}' results/15/control/mcp-agent.json
```

Оба ответа должны опираться на одну заметку: выход `q`, пауза `p`. Проверь не только ответ, но и путь: в первом запуске ожидается действие `read_file`, во втором — `mcp_call` с обнаруженным именем `read_note`. Затем в трассе второго найди фактический `tools/call`. Само `tools/list` могло выполниться в обоих запусках при подключении возможностей.

Если модель выбрала другой маршрут, ответ не засчитывается как демонстрация требуемого способа вызова, даже если буквы совпали. Этот опыт не предполагает, что MCP улучшит знания модели: при одинаковых данных ответы могут совпасть. Добавляется способ интеграции инструментов.

### Измени заметку вместо промпта

Сначала закончи предыдущую пару. Затем замени только входной файл:

```bash
cp lessons/15-mcp/fixtures/notes-b.txt results/15/workspace/notes.txt
/usr/bin/python3 -m coursekit mcp-demo --workspace results/15/workspace > results/15/control/mcp-version-b.json
/usr/bin/python3 -m coursekit agent --task-file lessons/15-mcp/prompts/variation.txt --workspace results/15/workspace --endpoint http://127.0.0.1:8088 --max-steps 6 --mcp --tools read_file,write_file,mcp_call --state results/15/control/version-b-state.json > results/15/control/version-b.json
```

Во второй версии выход назначен `x`, пауза — `space`. Найди новые данные сначала в результате реального инструмента, затем в ответе модели. Если модель продолжает отвечать `q` и `p`, выясни, прочитала ли она заметку и какие данные реально попали в контекст. Новый ответ не требует дообучения весов.

## Ожидаемые наблюдения

Без модели программа может установить соединение, получить схему, вызвать инструмент и обработать отказ. Модель добавляет выбор действия внутри управляемого цикла. Два маршрута чтения могут дать одинаковое содержимое; протокол меняет границу между программами, а не истинность заметки.

Проверки схемы и пути исполняются независимо от послушания модели. Содержимое заметки остаётся недоверенными данными даже после успешного MCP-вызова.

## Если результат отличается

Если сервер печатает обычный текст в stdout, клиент может не разобрать JSON-RPC. Диагностика должна идти отдельным каналом. Если вызов завис, работает таймаут клиента; успешный повтор не нужен, пока не разобран жизненный цикл процесса. Не добавляй запуск через shell или произвольный executable ради обхода ошибки.

Если неизвестный инструмент или неверные аргументы отклонены, это ожидаемый отрицательный опыт. Если после отказа следующий валидный вызов не работает, сохрани протокольную трассу. Не выдавай словарь с заранее готовой заметкой за подтверждение работающего MCP.

## Что сохранить

Сохрани `mcp-demo.json`, результат проверки локального сервера, два запуска агента и пару результатов после изменения заметки. Рядом нарисуй цепочку: текст задачи → действие модели → вызов клиента → JSON-RPC → операция сервера → результат инструмента → следующий вход модели. Для каждого звена укажи владельца и место проверки полномочий.

## Критерии завершения

- В журнале настоящего локального процесса видны инициализация, обнаружение и вызов инструмента.
- Отрицательные проверки не читают данные вне разрешённого каталога; клиент после них способен продолжить работу.
- Клиент закрывает дочерний процесс; проверка не оставляет сервер в фоне.
- В опыте с моделью ты различаешь подключение MCP и фактический выбор MCP-инструмента.
- Изменение заметки прослежено до результата инструмента и ответа модели либо сохранено и разобрано расхождение.
- Запуски без LLM и с реальной моделью отмечены отдельно.

## Свой эксперимент

Отключи флаг `--mcp`, оставив промпт второго маршрута прежним. Предскажи, как harness обработает предложение недоступного инструмента. Правильный результат — понятный ограниченный отказ или честное объяснение недоступности, а не выдуманный результат чтения. Затем обсуди, почему обычный `read_file` остаётся другой доступной возможностью и почему знание содержимого само по себе не доказывает маршрут.
