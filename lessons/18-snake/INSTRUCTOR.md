# Преподавание итоговой практики со Змейкой

## Статус единой лаборатории

Маршрут этого урока после обновлённых 00–04 проработан в [LABORATORY_PLAN.md](LABORATORY_PLAN.md), но ещё не перенесён в рабочее поле. Ниже сохранён прежний технический маршрут; он не является готовым продолжением новой лаборатории.


Перед занятием прочитайте [руководство преподавателя](../../course/TEACHER_GUIDE.md): оно задаёт порядок подсказок, возврата к исходной ошибке и проверки самостоятельного переноса.

## Вход в занятие до прогнозов

Прочитайте с учеником [введение](INTRO.md). Начните с первого абзаца задания и фактических свидетельств согласования из урока 17. Пусть ученик объяснит, что показал `show`, где находятся принятые документы и кто будет принимать игру. Только затем обсуждайте прогноз действий и бюджет; шаблон задания не заменяет отсутствие требуемых артефактов.

Если ученик не понимает, зачем вводить команду или какой текст читать, вернитесь к её назначению, точному объекту и ожидаемому виду результата. Продолжайте после его объяснения своими словами, а не после одного «готово».

## Подготовка преподавателя

Проверь, что игра не была заранее создана в учебных материалах. Приёмка должна опираться на утверждённую спецификацию ученика, а не на неявные ожидания преподавателя.

До урока подготовь модель, контейнерный образ, права на безопасный workspace и возможность ручной работы с TTY. Зафиксируй версии. Состояния и исходные критерии вне каталога записи агента. Не запускай игру на хосте при неполадках контейнера.

Прочитай HEADLESS.md и fixtures/headless_cases.json. Если ученик принял другой профиль правил, адаптируйте критерии до генерации кода. Check_snake не объявляет модель проверенной и не заменяет ручную приёмку.

## План на 90 минут

| Минуты | Работа преподавателя |
| --- | --- |
| 0–10 | Ученик предсказывает нужные компоненты и проверки |
| 10–35 | Агент пишет игру и выполняет проверки, преподаватель наблюдает |
| 35–50 | Независимый checker, разбор конкретного перехода |
| 50–65 | Одно ограниченное исправление по настоящему отчёту |
| 65–80 | Игра в TTY, обычный выход и прерывание |
| 80–90 | Разбор трассы и итоговый протокол приёмки |

Для 75 минут сократи число дополнительных игровых предпочтений, но сохрани автоматическую и ручную приёмку. Для 60 минут раздели практику на два подхода с сохранением состояния: создание и автоматические проверки, затем ручная приёмка. Если модель слишком медленная, ожидание не превращается в якобы завершённое активное занятие; выбери заранее проверенный профиль ресурсов.

## Вопросы и ответы преподавателю

1. Почему недостаточно bash -n? Проверка синтаксиса не проверяет движение, столкновения, рост, клавиши и восстановление терминала.
2. Кто придумал ожидаемый результат для теста? Он выведен из принятого правила до реализации, а не из фактического ответа игры.
3. Почему checker не берёт тесты из workspace? Агент мог бы незаметно ослабить их. Доверенный checker находится вне его полномочий.
4. Почему наличие успешного контейнерного отчёта не доказывает качество модели? Это свидетельство поведения данной реализации; происхождение кода и взаимодействие с моделью подтверждает отдельная трасса.
5. Что означает finish в задаче реализации? Агент считает свою ограниченную задачу завершённой. Полная приёмка курса также требует независимой проверки и действий человека.
6. Почему для исправления после finish используется новая задача? Завершённое состояние не должно повторно вызывать модель при resume без новой задачи.
7. Зачем ручная проверка TTY? Headless-проверка не исполняет чтение клавиш и настройку терминала.

## Типичные заблуждения

«Рефлексия обязательно улучшает код». Исправление имеет смысл только относительно проверенного наблюдения. Модель может внести регрессию.

«Модель прошла тест, потому что заявила об этом». Попроси найти фактический вызов, код завершения и stdout.

«Если tests прошли, требования менять уже нельзя». Новое пользовательское решение проходит уточнение и обновление спецификации; затем нужны новые проверки и проверка регрессий.

«Чтобы ускорить, можно дать модельному shell доступ к хосту». Это нарушает предмет опыта о контролируемом исполнении. Неработающий контейнер — явная остановка, а не причина убирать границу.

## Вмешательства преподавателя

Если агент переписывает требования ради успеха, сравни с защищённой копией. Если он меняет независимый checker, соответствующий инструмент должен отказать из-за границы workspace.

Если после реального неуспеха агент повторяет один и тот же запуск без изменения гипотезы или кода, останови цикл. Разбери, какой вход и ожидаемый переход он не учитывает.

Если автоматические проверки прошли сразу, не создавай ложный лог ошибки. Выбери дополнительный согласованный сценарий или проведи опыт с небольшой контролируемой регрессией в отдельной копии реализации.

Если ручной запуск прерван, проверь только именованный контейнер этого опыта и заверши его. Не оставляй процессы после урока.

## Критерии итогового понимания

Попроси ученика объяснить одну запись файла и одно исправление по всей цепочке: задача → вход модели → предложенное действие → решение политики → контейнер → наблюдение → следующий запрос. Затем предложи убрать один компонент и предсказать, что перестанет работать.

Успешная практика имеет заполненный ручной протокол, независимый автоматический отчёт и трассу настоящих запросов к модели. Синтетический fixture-report показывает только работоспособность проверяющего кода.

## Дополнительный опыт

Новое требование о паузе или скорости должно сначала появиться в обсуждении и спецификации. Сравнить число исправлений с вариантом, когда требование добавили прямо во время кодирования. Не делать вывод о превосходстве по одной попытке.


## Совместное наблюдение в терминале

Используйте [общий порядок совместного занятия](../../course/TERMINAL_CLASSROOM.md). Ученик открывает `./lab classroom start --lesson 18 --sandbox-image llm-course-sandbox:1.0`. Преподаватель находит сессию через `./lab classroom list`, читает события через `observe SESSION --json` и просит прогноз до первого запуска.

Для этого этапа исходный набор компонентов: `./lab classroom permit SESSION --capabilities doctor,complete,agent,bash,skill`. После проверки подготовки преподаватель выполняет `./lab classroom resume SESSION`. На разборе результата он использует `pause`, для прерывания активного опыта — `stop` и проверяет фактическое подтверждение.

Советы передавайте через `./lab classroom advise SESSION --message 'Текст следующего вопроса или опыта'`. Ученик отвечает и меняет вход самостоятельно. Дополнительные программы из методички, не подключённые к диспетчеру, обсуждайте отдельно: открытая консоль сама по себе не даёт наблюдение и остановку всех процессов ноутбука.
