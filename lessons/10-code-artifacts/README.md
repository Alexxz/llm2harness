# Создание кода и проверка артефакта

## Статус единой лаборатории

Маршрут этого урока после обновлённых 00–04 проработан в [LABORATORY_PLAN.md](LABORATORY_PLAN.md), но ещё не перенесён в рабочее поле. Ниже сохранён прежний технический маршрут; он не является готовым продолжением новой лаборатории.


Сначала прочитай [введение и первый шаг](INTRO.md): там объяснены смысл опыта, участники и конкретный текст для чтения. Блоки подготовки и опытов ниже предназначены для обычного Bash-терминала. В приглашении `ученик>` используй команды учебной консоли из введения и указаний преподавателя.

Для совместной работы открой [учебную консоль с преподавателем](../../course/TERMINAL_CLASSROOM.md): `./lab classroom start --lesson 10` из корня проекта. Промпты, явные запуски и советы этой сессии видны преподавателю; обычные команды других терминалов в журнал не попадают.


## Цель

Разделить предложение модели, запись файла и исполнение кода. Ты получишь небольшой Bash-скрипт и проверишь его независимым набором входов. Модель создаёт текст действия; harness проверяет действие, записывает разрешённый файл и передаёт запуск контейнеру.

Это первое занятие с исполняемым артефактом. Базовая политика уже действовала в занятиях 08–09. Здесь добавляется реальная изоляция исполнения.

## Перед началом

Нужны занятия [08](../08-first-tool/README.md) и [09](../09-agent-loop/README.md), работающая модель для инструкций, сервер на `http://127.0.0.1:8088` и подготовленный контейнерный образ стенда. Сохрани идентификатор модели, версию runtime и настройки из предыдущего занятия. Во всех сравнениях используй одну версию модели.

Из корня проекта проверь готовность:

```bash
./lab doctor
mkdir -p results/lesson10/baseline
./lab sandbox-check --workspace results/lesson10/baseline
```

Если Docker daemon недоступен, образ не подготовлен или проверка изоляции не прошла, сначала разбери инфраструктурную причину. Временная недоступность контейнера не превращает запуск в локальный `bash greet.sh`. Не меняй в обход отказа параметры изоляции. Во время занятия контейнер получает readonly снимок выделенного рабочего каталога и ограниченную рабочую копию в памяти; изменения возвращаются через проверенный экспорт; домашние каталоги, управляющий socket Docker и внешняя сеть ему не передаются.

## План занятия

За 75 минут: 10 минут — контракт и прогноз; 15 — первый запуск; 15 — независимая проверка; 20 — вариант с запросом проверки; 10 — разбор трассы; 5 — собственная гипотеза. Подготовка образа и весов выполняется до занятия.

## Опыты

### Опыт 1 — Получить исполняемый файл

Сначала прочитай исходный промпт:

```bash
./lab prompt 10 baseline
```

До запуска запиши прогноз: сколько действий потребуется, кто создаст файл и какие проверки модель действительно запросит. Контракт в промпте полностью определён. Имя — данные, а не фрагмент программы. Например, имя `Мир и Оля` должно остаться одним аргументом.

Запусти агента в новом каталоге:

```bash
./lab agent --task-file lessons/10-code-artifacts/prompts/baseline.txt --workspace results/lesson10/baseline --endpoint http://127.0.0.1:8088 --max-steps 8 --tools read_file,write_file,run_bash --state results/lesson10/baseline-state.json > results/lesson10/baseline-run.json
```

Прочитай файл как текст и журнал действий. Не запускай созданный скрипт непосредственно на хосте. Найди отдельно: ответ модели с `write_file`, решение harness, результат записи и возможный `run_bash`. Текст «проверил» в финальном ответе не заменяет событие исполнения.

### Опыт 2 — Проверить независимым оракулом

Оракул — заранее подготовленная проверка требований. Он не извлекает ожидаемый результат из созданного скрипта. Посмотреть его тесты можно без контейнера и без модели:

```bash
/usr/bin/python3 lessons/10-code-artifacts/check.py --describe
```

Запусти проверку через контейнер:

```bash
/usr/bin/python3 lessons/10-code-artifacts/check.py --workspace results/lesson10/baseline > results/lesson10/baseline-check.json
```

Проверяются синтаксис, обычное имя, пробелы, пустой аргумент, буквальные символы оболочки, отсутствие аргумента и лишний аргумент. Проверка сохраняет настоящий stdout, stderr и код возврата контейнера. Ввод с символами оболочки передаётся как аргумент; ни проверка, ни harness не должны превращать его в код.

Значение `pass: true` относится к этому набору входов и данному файлу. Оно не доказывает правильность любой Bash-программы. Ошибка контейнера или таймаут — результат проверки среды, а не сообщение о неправильной строке приветствия.

### Опыт 3 — Изменить только требование проверки

Во втором промпте добавлен один пункт: агент должен запросить проверку и исправить найденное до завершения. Функциональный контракт остаётся прежним.

```bash
mkdir -p results/lesson10/variation
./lab agent --task-file lessons/10-code-artifacts/prompts/variation.txt --workspace results/lesson10/variation --endpoint http://127.0.0.1:8088 --max-steps 8 --tools read_file,write_file,run_bash --state results/lesson10/variation-state.json > results/lesson10/variation-run.json
/usr/bin/python3 lessons/10-code-artifacts/check.py --workspace results/lesson10/variation > results/lesson10/variation-check.json
```

Сравни количество действий, фактически запрошенные проверки и независимый результат. Остальные условия сохраняй: модель, настройки генерации, бюджет шагов, образ и исходно пустой каталог. Если оба варианта проходят, это нормальное наблюдение: добавленная инструкция могла изменить дисциплину проверки без улучшения уже правильного результата.

## Ожидаемые наблюдения

Ты должен увидеть цепочку от текста действия до файла и от файла до изолированного запуска. Один синтаксический успех не гарантирует выполнение требований: скрипт может разбирать два слова имени как два аргумента или неверно обрабатывать пустую строку.

Более подробный запрос проверки может увеличить число действий и расход контекста. Как изменится доля успешных запусков конкретной модели, устанавливается экспериментом. В методичке нет заранее измеренной доли успеха.

## Если результат отличается

- Ответ содержит Markdown вместо действия: это ошибка контракта действий. Проверь исходный запрос и журналы валидации; не исполняй извлечённый текст вручную.
- Файл не появился: найди последний результат `write_file`, отказ политики или исчерпание бюджета.
- Агент написал «всё готово», а оракул нашёл ошибку: зафиксируй расхождение и переходи к разбору обратной связи в занятии 11.
- `bash -n` прошёл, а функциональная проверка упала: сравни конкретный вход, stdout, stderr и код возврата.
- Контейнер не стартовал: запиши инфраструктурный отказ и вернись к проверке среды; качество модели по нему не оценивается.

## Что сохранить

Сохрани оба промпта, идентификатор модели, настройки, два каталога с исходниками, состояния, журналы и независимые отчёты проверок. Рядом запиши прогноз и наблюдение: какое действие выполнила модель и какое выполнил harness.

## Критерии завершения

1. Ты можешь показать запись `write_file` и соответствующий файл.
2. Как минимум один полученный моделью вариант прошёл контейнерный оракул. Если он не прошёл, сохрани точную причину и разбери исправление в занятии 11; до успешной проверки приёмка исполнения остаётся открытой.
3. Для сравнительной таблицы приведены реальные действия и реальные отчёты, включая неуспешные.
4. Ты объясняешь различие между синтаксисом, функциональным контрактом и изоляцией исполнения.

При подготовке курса написаны инструкции и оракул. Практика с моделью и контейнерный прогон принимаются только по сохранённым результатам запуска.

## Свой эксперимент

Добавь одно новое имя, которое ещё не встречалось в проверках: например, строку с кавычкой или ведущим дефисом. Сначала вычисли ожидаемые байты и код возврата независимо от модели, затем расширь оракул и запусти тот же файл. Не изменяй одновременно и требования к скрипту, и версию модели.
