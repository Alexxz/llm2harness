# Проведение занятия о создании кода

Перед занятием прочитайте [руководство преподавателя](../../course/TEACHER_GUIDE.md): оно задаёт порядок подсказок, возврата к исходной ошибке и проверки самостоятельного переноса.

## Вход в занятие до прогнозов

Прочитайте с учеником [введение](INTRO.md). Сначала ученик различает текст задачи, предполагаемый файл и проверку поведения. Попросите его объяснить, что покажет `show`, какой объект он прочитает и создастся ли от этого `greet.sh`. Затем обсудите выбранную им проверку требований. Прогноз цепочки действий модели запрашивайте после этого объяснения и проверки готовности контейнера.

Если ученик не понимает, зачем вводить команду или какой текст читать, вернитесь к её назначению, точному объекту и ожидаемому виду результата. Продолжайте после его объяснения своими словами, а не после одного «готово».

## Подготовка

До занятия проверь сервер модели, фактическую доступность Docker daemon и наличие подготовленного образа. Запусти штатный `sandbox-check`, а затем контейнерный оракул на заранее проверенном преподавателем учебном решении в отдельной рабочей папке. Такой прогон проверяет стенд; он не является результатом генерации модели. Не выдавай его за результат ученика и не клади решение в его пустой рабочий каталог.

Проверь, что в изоляцию попадает только каталог опыта, сеть отключена и управляющий socket Docker не смонтирован. Объясни, какие ограничения установлены программой курса и какие — контейнером. Не обещай абсолютную защищённость от уязвимостей ядра или Docker.

## План на 75 минут

| Время | Действие |
|---|---|
| 0–10 | Ученик читает контракт и прогнозирует цепочку действий. |
| 10–25 | Выполняет baseline, сопоставляет ответы и файлы. |
| 25–40 | Читает независимые проверки и получает фактический отчёт. |
| 40–60 | Выполняет variation в новом каталоге и сравнивает. |
| 60–70 | Разбирает исполнение, ошибки и границы полномочий. |
| 70–75 | Формулирует собственный эксперимент и сохраняет выводы. |

## Вопросы и ориентиры ответов

**Кто создал файл?** Модель предложила `write_file`; запись выполнил доверенный код harness после проверки. Показать оба события.

**Где исполнился Bash?** В отдельном контейнере, запущенном `DockerSandbox`. Текущая папка сама по себе не создаёт такую границу.

**Почему не хватает bash -n?** Он проверяет синтаксис; требования к аргументам, выводу и exit code проверяются другими входами.

**Зачем проверять имя с символами оболочки?** По контракту аргумент является данными. Его буквальная передача проверяет, не возникло ли дополнительной интерпретации.

**Оба промпта прошли. Опыт бесполезен?** Нет. Сравниваются также реально выполненные действия, стоимость проверки и честность заявления о готовности. Улучшение качества не предполагается заранее.

**Почему проверки лежат вне доступного агенту каталога?** Ожидаемый результат определяется контрактом и проверяющим кодом, независимо от создаваемого файла. Ученик может читать код оракула для понимания.

## Типичные заблуждения

- «LLM запускает Bash». Попроси найти в трассе границу между JSON модели и запуском.
- «Выход 0 означает, что задача решена». Предложи скрипт, который всегда завершается успешно и ничего не печатает.
- «Есть список инструментов — значит есть sandbox». Покажи, что политика допуска действий и изоляция процесса отвечают на разные вопросы.
- «Повторить ещё десять раз достаточно для доказательства». Попроси сначала определить, какие условия фиксируются и какая гипотеза проверяется.

## Вмешательства преподавателя

Если модель срывает контракт действия, помоги разобрать один конкретный ответ, но не переписывай её артефакт незаметно. Ручное исправление подпиши как отдельное вмешательство. Если модель не справляется в отведённом бюджете, сохранить неуспех полезнее бесконечных перезапусков: следующий урок посвящён ремонту.

Если Docker недоступен, можно разобрать `--describe` и текст трассы, но занятие помечается как неполная практика исполнения. Код на хосте не запускается.

## Сокращение до 60 минут

Сохрани baseline, реальную независимую проверку и сравнение с variation. Собственный эксперимент становится домашним. Не убирай разбор того, где именно исполнялся код.

## Расширение до 90 минут

Проведи второй независимый запуск каждого варианта с теми же настройками. Построй таблицу исходов без вывода о статистически доказанном превосходстве по двум запускам. Обсуди, какую дополнительную выборку и метрику пришлось бы подготовить.

## Приёмка преподавателем

Проверь наличие артефакта, отчёта контейнера, журналов и объяснения четырёх границ: текст модели, запись файла, запуск процесса, оценка требований. Статусы подготовки материалов, проверки стенда и живого опыта должны оставаться раздельными.


## Совместное наблюдение в терминале

Используйте [общий порядок совместного занятия](../../course/TERMINAL_CLASSROOM.md). Ученик открывает `./lab classroom start --lesson 10`. Преподаватель находит сессию через `./lab classroom list`, читает события через `observe SESSION --json` и просит прогноз до первого запуска.

Для этого этапа исходный набор компонентов: `./lab classroom permit SESSION --capabilities doctor,complete,agent,bash`. После проверки подготовки преподаватель выполняет `./lab classroom resume SESSION`. На разборе результата он использует `pause`, для прерывания активного опыта — `stop` и проверяет фактическое подтверждение.

Советы передавайте через `./lab classroom advise SESSION --message 'Текст следующего вопроса или опыта'`. Ученик отвечает и меняет вход самостоятельно. Дополнительные программы из методички, не подключённые к диспетчеру, обсуждайте отдельно: открытая консоль сама по себе не даёт наблюдение и остановку всех процессов ноутбука.
