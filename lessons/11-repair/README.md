# Исправление кода по результату выполнения

Сначала прочитай [введение и первый шаг](INTRO.md): там объяснены смысл опыта, участники и конкретный текст для чтения. Блоки подготовки и опытов ниже предназначены для обычного Bash-терминала. В приглашении `ученик>` используй команды учебной консоли из введения и указаний преподавателя.

Для совместной работы открой [учебную консоль с преподавателем](../../course/TERMINAL_CLASSROOM.md): `./lab classroom start --lesson 11` из корня проекта. Промпты, явные запуски и советы этой сессии видны преподавателю; обычные команды других терминалов в журнал не попадают.


## Цель

Проверить, что агент умеет использовать фактическую ошибку для следующего решения. Ты сравнишь два запуска с одним исходным дефектом: в первом модель получает только контракт, во втором — тот же контракт и независимый отчёт контейнерной проверки.

Изменяются сообщения в контексте. Веса модели во время ремонта не обучаются.

## Перед началом

Пройди [занятие 10](../10-code-artifacts/README.md). Нужны та же версия модели, подготовленный образ и прошедший проверку контейнерный стенд. Код примера `sum-lines.sh` — специально подготовленная ошибочная фикстура, а не результат модели.

Подготовь два одинаковых начальных каталога. Скрипт подготовки отказывается перезаписывать непустую папку.

```bash
/usr/bin/python3 lessons/11-repair/prepare.py --workspace results/lesson11/baseline
/usr/bin/python3 lessons/11-repair/prepare.py --workspace results/lesson11/variation
./lab sandbox-check --workspace results/lesson11/baseline
```

Состояния и авторитетные журналы хранятся рядом с каталогами, но за пределами доступной агенту рабочей области.

## План занятия

За 80 минут: 10 — предсказание; 15 — исходное измерение; 15 — ремонт без отчёта; 20 — ремонт с отчётом; 15 — сравнение реальных действий; 5 — собственная гипотеза. Не трать всё время на перезапуски одного неуспешного варианта.

## Опыты

### Опыт 1 — Измерить исходный дефект

Прочитай контракт в исходном промпте и посмотри код как текст. Предскажи результаты для обычного файла `1\\n2\\n3\\n`, того же набора чисел без последнего перевода строки, пустого файла и одного числа без перевода строки.

Проверки можно изучить без запуска:

```bash
/usr/bin/python3 lessons/11-repair/check.py --describe
```

Получение настоящего исходного отчёта:

```bash
mkdir -p results/lesson11/reports
/usr/bin/python3 lessons/11-repair/check.py --workspace results/lesson11/baseline > results/lesson11/reports/before.json
```

Ненулевой exit code проверки ожидаем, если фикстура действительно не выполняет контракт. Не продолжай по ошибке `execution_unavailable`: сначала восстанови контейнерную среду. При успешном выполнении оракула отчёт имеет `status: checked`, даже если отдельные случаи не прошли.

Случаи оракула создают свои входы внутри контейнера. Изменение агентом демонстрационных файлов `inputs/` не изменит ожидаемые ответы проверки.

### Опыт 2 — Ремонт по одному контракту

```bash
./lab agent --task-file lessons/11-repair/prompts/baseline.txt --workspace results/lesson11/baseline --endpoint http://127.0.0.1:8088 --max-steps 10 --tools read_file,write_file,run_bash --state results/lesson11/baseline-state.json > results/lesson11/baseline-run.json
/usr/bin/python3 lessons/11-repair/check.py --workspace results/lesson11/baseline > results/lesson11/reports/baseline-after.json
```

Отметь, читал ли агент файл, выполнял ли проверки и менял ли код после их результатов. Он может найти дефект по чтению исходника. Поэтому успех без входного отчёта сам по себе не доказывает, что проверка не нужна.

### Опыт 3 — Дать независимую обратную связь

Второй запуск начинается с той же фикстуры в `variation`. Сначала убедись, что исходная проверка на этом каталоге даёт те же функциональные исходы, что `before.json`:

```bash
/usr/bin/python3 lessons/11-repair/check.py --workspace results/lesson11/variation > results/lesson11/reports/variation-before.json
```

Собери запрос из исходного контракта и фактического отчёта. Рендерер принимает только завершённый контейнерный отчёт. Он не подтверждает подлинность внешнего файла: ты указываешь созданный здесь результат проверяющего кода.

```bash
/usr/bin/python3 lessons/11-repair/build_task.py --report results/lesson11/reports/variation-before.json --output results/lesson11/task-with-feedback.txt
./lab agent --task-file results/lesson11/task-with-feedback.txt --workspace results/lesson11/variation --endpoint http://127.0.0.1:8088 --max-steps 10 --tools read_file,write_file,run_bash --state results/lesson11/variation-state.json > results/lesson11/variation-run.json
/usr/bin/python3 lessons/11-repair/check.py --workspace results/lesson11/variation > results/lesson11/reports/variation-after.json
```

Меняется только наличие входного отчёта. Модель, исходный файл, контейнер, бюджет и требования остаются теми же. Не подставляй вместо фактического отчёта выдуманный успешный результат.

### Опыт 4 — Проследить исправление

Для каждого запуска сопоставь: исходное наблюдение, предложенное изменение, действие записи и последующую проверку. Ответ «исправил» без изменения файла или проверяемого результата не подтверждает исправление.

Построй таблицу: вариант, исправленный дефект, реальные проверки агента, независимые проверки после него, число действий, причина остановки. Оба варианта могут пройти или оба могут не пройти. Это исходы конкретного опыта; для вывода о надёжности нужны повторные контролируемые запуски.

## Ожидаемые наблюдения

Проверка файла с завершающим переводом строки может пройти, пока крайний случай остаётся сломан. Результат работы инструмента добавляет модели сведения о конкретном поведении программы.

Исправление может добавить другую ошибку. Поэтому после ремонта повторяется весь набор проверок, а не только последний неуспешный случай. Новый ответ модели не обновляет веса ядра: меняется контекст и создаваемый артефакт.

## Если результат отличается

- Исходная фикстура прошла всё: проверь её происхождение и соответствие сценарию. Возможно, каталог уже содержал исправленный файл.
- Модель изменила входные примеры: сравни их с оригиналом; независимый оракул всё равно создаёт собственные входы.
- В отчёте таймаут или отказ контейнера: это ещё не наблюдение о суммировании.
- Ремонт остановился по бюджету: сохрани незавершённый запуск и его причину. Увеличение бюджета — отдельный следующий опыт.
- Финальный ответ уверен, но проверки не прошли: оцени фактический артефакт и объясни расхождение.

## Что сохранить

Сохрани исходную и исправленную версии кода, исходные и последующие отчёты, сформированный промпт с обратной связью, журналы, состояния и идентификатор модели. Укажи, какие выводы опираются на запуск, а какие пока являются гипотезой.

## Критерии завершения

1. Исходный дефект воспроизведён настоящим контейнерным запуском.
2. Сохранено сопоставимое сравнение ремонта с входным отчётом и без него.
3. Исправленный артефакт прошёл полный независимый набор проверок хотя бы в одном варианте.
4. По трассе можно восстановить, от какого наблюдения агент перешёл к какому изменению.
5. Ты объясняешь, почему это обратная связь выполнения и почему она не является дообучением.

До фактического запуска модели и контейнера эти критерии являются условиями приёмки, а не зарегистрированными успехами.

## Свой эксперимент

Измени только детализацию обратной связи: передай краткий список неуспешных случаев вместо полного отчёта. Начни с новой копии той же фикстуры. Сравни результат, число запросов и фактически выполненные проверки. Полный отчёт может оказаться полезнее, избыточнее или не изменить результат — заранее не выбирай победителя.
