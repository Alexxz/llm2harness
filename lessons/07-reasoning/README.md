# Рассуждение и независимая проверка

Начни с [введения в урок](INTRO.md): оно объясняет новый механизм, роль консоли и первое действие до выполнения команд из подробного маршрута ниже.

В этом занятии модель по-прежнему получает текст и возвращает текст. Ты сравнишь прямой ответ и ответ с кратким наблюдаемым планом, затем проверишь оба независимой программой. Веса, инструменты модели и устройство нейросети остаются прежними.

Для совместной работы открой [учебную консоль с преподавателем](../../course/TERMINAL_CLASSROOM.md): `./lab classroom start --lesson 07` из корня проекта. Промпты, явные запуски и советы этой сессии видны преподавателю; обычные команды других терминалов в журнал не попадают.


## Цель

Различать полезность плана, убедительность объяснения и правильность результата. После занятия ты можешь указать, какой вывод дала модель, что проверила программа и почему текст плана сам по себе не доказывает доступ к внутренним вычислениям модели.

В исследованиях prompting с промежуточными шагами помогал на определённых задачах и моделях. Это основание поставить опыт, а не обещание улучшения на каждом примере. [Wei et al.](https://arxiv.org/abs/2201.11903). Проверять надо и результат, и объяснение: существуют эксперименты с правдоподобными, но неверными объяснениями. [Turpin et al.](https://arxiv.org/abs/2305.04388).

## Перед началом

Работай из корня проекта. Заверши занятия 01–06. Подготовленный сервер ядра должен слушать `http://127.0.0.1:8088`; запуск и выбор весов описаны в общем ресурсном плане. В этом занятии новые модели не загружаем и обучение не запускаем.

Запиши имя и ревизию весов, наличие адаптера, шаблон входа и настройки. Для пары опытов используй одну конфигурацию модели, `temperature=0`, `seed=42`, максимум 256 новых токенов. Предел одинаковый для обоих ответов; если план обрезается, увеличь его для обоих и повтори сравнение.

```bash
/usr/bin/python3 -m coursekit doctor
mkdir -p results/lesson07
/usr/bin/python3 -m coursekit prompt 07 baseline
```

## План занятия

| Минуты | Работа |
|---|---|
| 0–10 | Сформулируй предположение о пользе плана и запиши критерий проверки. |
| 10–20 | Разбери складскую задачу и независимый проверяющий код. |
| 20–40 | Получи два настоящих ответа, сравни их по одинаковым правилам. |
| 40–55 | Проверь заданный ошибочный ответ с убедительным планом. |
| 55–65 | Верни фактический результат проверки модели и повторно проверь ответ. |
| 65–75 | Предложи собственный опыт и объясни границы вывода. |

## Опыты

### Прямой ответ

Прочитай [исходный промпт](prompts/baseline.txt). В нём заданы начальный остаток, поступления, продажи, возврат и резерв. Резерв остаётся на складе, но уменьшает доступный остаток.

Сначала запиши свою оценку: какие ошибки возможны и позволит ли JSON заметить арифметическую ошибку. Затем выполни настоящий запрос:

```bash
/usr/bin/python3 -m coursekit complete --prompt-file lessons/07-reasoning/prompts/baseline.txt --endpoint http://127.0.0.1:8088 --max-tokens 256 --temperature 0 --seed 42 --output results/lesson07/direct.json
/usr/bin/python3 lessons/07-reasoning/check_inventory.py --response results/lesson07/direct.json
```

Файл результата `complete` содержит `text`, метаданные и события. Проверяющая программа извлекает `text` и разбирает JSON строго: блоки Markdown и комментарии считаются ошибкой формата.

### Краткий план

Меняется только инструкция о представлении ответа: [вариант промпта](prompts/variation.txt) дополнительно просит два пункта плана проверки. Исходные данные и параметры запроса остаются теми же.

```bash
/usr/bin/python3 -m coursekit complete --prompt-file lessons/07-reasoning/prompts/variation.txt --endpoint http://127.0.0.1:8088 --max-tokens 256 --temperature 0 --seed 42 --output results/lesson07/with-plan.json
/usr/bin/python3 lessons/07-reasoning/check_inventory.py --response results/lesson07/with-plan.json
```

Сравни `format_ok`, `correct`, число сгенерированных токенов и время в метаданных. Отдельно прочитай план: соответствует ли он определениям физического и доступного остатка? Наличие двух пунктов не означает, что их содержание правильно.

### Независимая проверка

Открой [проверяющую программу](check_inventory.py) и [исходные данные](fixtures/cases.json). Она выполняет обычные целочисленные операции, а не спрашивает другую модель. Модель не получает вычисленный эталон до завершения первых двух опытов.

```bash
/usr/bin/python3 lessons/07-reasoning/check_inventory.py --case base
/usr/bin/python3 lessons/07-reasoning/check_inventory.py --response lessons/07-reasoning/fixtures/correct.json
/usr/bin/python3 lessons/07-reasoning/check_inventory.py --response lessons/07-reasoning/fixtures/plausible_wrong.json
```

Последняя команда должна вернуть `format_ok=true`, `correct=false` и код завершения 1. Это намеренно заданный ошибочный ответ с планом, а не найденная ошибка реальной модели. Так мы проверяем, способен ли наш проверяющий код различить формат и содержание.

Эталон для исходной задачи: физический остаток 159, доступный 144. Объясни, почему резерв уменьшает второе число, но не первое.

### Обратная связь проверки

Выбери один из собственных ответов. Если он неверен, сохрани конкретное расхождение; если оба верны, используй отдельно обозначенный ошибочный пример из предыдущего опыта. Создай `results/lesson07/feedback.txt`: исходная задача, выбранный ответ, фактический вывод `check_inventory.py` и просьба вернуть исправленный JSON. Достаточно скопировать текст; код писать не требуется.

```bash
/usr/bin/python3 -m coursekit complete --prompt-file results/lesson07/feedback.txt --endpoint http://127.0.0.1:8088 --max-tokens 256 --temperature 0 --seed 42 --output results/lesson07/after-check.json
/usr/bin/python3 lessons/07-reasoning/check_inventory.py --response results/lesson07/after-check.json
```

Это новый запрос с добавленным наблюдением. Веса модели не меняются. Если ответ исправился, мы подтвердили исправление на этом входе, а не самостоятельную способность всегда находить ошибки.

## Ожидаемые наблюдения

- Проверка стенда принимает заданный правильный пример и отвергает заданный неправильный, хотя оба являются JSON.
- Два настоящих ответа сравниваются на одних данных. Улучшение от плана не предполагается заранее: оба ответа могут быть верны, неверны или отличаться только длиной.
- Обратная связь появляется в новом тексте запроса. Проверяющая программа остаётся внешней по отношению к модели.
- Краткий план — наблюдаемый текст. Он не является полным протоколом внутренних вычислений.

## Если результат отличается

Если JSON обрезан, посмотри причину завершения и одинаково увеличь лимит у обеих ветвей. Если появились ограждения Markdown, запиши ошибку формата; отдельным опытом можно применить [общую схему](inventory.schema.json) к обоим промптам через `--schema`, сохранив равные условия. Не добавляй схему только одной ветви сравнения.

Если оба ответа всегда верны, это нормальный результат. Возьми случай `small` или `no_reserve` из `cases.json`, одинаково обнови исходные данные в обоих промптах и вызови проверку с соответствующим `--case`. Не усложняй задачу до первой ошибки без учёта всех предыдущих результатов.

Если после обратной связи модель по-прежнему ошибается, остановись после двух попыток. Запиши ограничение модели и предложи передать вычисление инструменту; это тема следующего занятия.

## Что сохранить

Сохрани оба промпта, конфигурацию модели, исходные JSON-файлы `complete`, вывод независимой проверки, текст обратной связи и краткую таблицу: вариант, формат, правильность, токены, время. Заданные фикстуры пометь отдельно от настоящих ответов.

## Критерии завершения

1. Выполнены два настоящих запроса с одной контролируемой разницей и сохранены их результаты.
2. Правильность проверена независимо; ученик может объяснить вычисление 159 и 144.
3. Заданный ошибочный ответ отклонён, несмотря на его план и корректный JSON.
4. Выполнен хотя бы один запрос с фактической обратной связью; его результат снова проверен.
5. Ученик объясняет, почему этот опыт не является дообучением и не открывает скрытые рассуждения модели.

## Свой эксперимент

Выбери одну переменную: порядок операций в тексте, размер резерва, необходимость плана или доступность результата проверки. До запуска запиши гипотезу и способ её опровергнуть. Сохрани и неудачный результат. Для изменения чисел обнови независимый источник эталона, а не только ожидаемый ответ в голове.
